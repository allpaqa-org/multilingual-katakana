## 0. 決定事項サマリー (Executive Summary)

| 区分 | 対象 | リリース | 配布形態 |
|---|---|---|---|
| ✅ **v0.4.0 スコープ** | **Node.js ネイティブバックエンド（NAPI-RS）** | v0.4.0 | 既存 `@allpaqa/multilingual-katakana` の `optionalDependencies` に、プラットフォーム別バイナリパッケージを追加 |
| ⏭️ 後続 | **Python バインディング（PyO3 + maturin）** | v0.5.0 | PyPI `multilingual-katakana`（abi3 wheel） |
| ⏭️ 後続 | **C# / .NET バインディング（C ABI + P/Invoke）** | v0.6.0 | NuGet `Allpaqa.MultilingualKatakana`（`runtimes/{rid}/native`） |
| 🕒 需要次第 | **スタンドアロン WebAssembly パッケージ（wasm-bindgen）** | 未定（v0.6.0 以降） | npm `@allpaqa/multilingual-katakana-wasm`（別パッケージ） |

**v0.4.0 の決定内容**:

1. v0.4.0 は **Node.js ネイティブバックエンドのみ** を出荷します。既存の公開 API（`toKatakana` / `KatakanaConverter` ほか全エクスポート）は **1 行も変更せず**、内部で「ネイティブが読み込めればネイティブ、読み込めなければ既存の Pure TypeScript 実装」へ自動で切り替わる **ドロップイン置換** とします。
2. **WASM フォールバックは v0.4.0 のメインパッケージに同梱しません。** 既存の Pure TypeScript 実装がすでにあらゆる JS ランタイム（Node / Bun / Deno / ブラウザ / Edge）で動作する「完全なフォールバック」であり、NAPI-RS 標準の WASI フォールバック（`wasm32-wasip1-threads`）は `@napi-rs/wasm-runtime` / `@emnapi/*` という JS ランタイム依存と、ブラウザでのクロスオリジン分離（COOP/COEP）を必要とするため、ゼロ依存原則と引き換えにする価値がないと判断しました。
3. Python・C#・スタンドアロン WASM は **別リリースへ分離** します。1 リリースで 4 ツールチェーン（NAPI-RS / PyO3 / C ABI / wasm-bindgen）と 4 レジストリ（npm / PyPI / NuGet / npm-wasm）を同時に立ち上げるのはリスクが高く、まず既存利用者がいる Node.js で「Rust コアをバインディング経由で配布する」パイプライン（ビルドマトリクス・適合性テスト・リリース手順）を確立し、後続バインディングはそれを再利用します。
4. 全バインディングは `spec/cases/*.json` を **各言語のネイティブなテストランナーから直接読み込み、パッケージング済み成果物に対して 100% パス** することをリリース条件とします。
5. バージョンは **全成果物ロックステップ（同一 `X.Y.Z`）** とします。

**なぜ Node.js ネイティブが最初か（v0.4.0 の価値とリスクの比較）**:

- **既存利用者への直接的な価値**: 現在の唯一の配布物が npm パッケージであり、Rust コア（2〜9 µs/フレーズ）の性能と「Rust コア = Single Source of Truth」の実体化を、利用者のコード変更ゼロで届けられます。
- **最小リスク**: Pure TypeScript 実装が完全なフォールバックとして既に存在し、仕様ケースで Rust と同一出力が保証されているため、ネイティブバイナリが無い／壊れている環境でも挙動は現状と変わりません（Safe Failure）。
- **後続フェーズの土台**: プラットフォーム別ビルドマトリクス、成果物に対する適合性テスト、複数パッケージのロックステップ公開という、Python/C# でも必要になる仕組みを最も利用者の多いターゲットで先に確立できます。

## 1. 前提と制約 (Constraints from `AGENTS.md`)

本計画は以下のプロジェクト原則を前提とし、これらを暗黙に破る実装は認めません。

1. **Zero Runtime Dependencies（完全ゼロ外部依存）**
   - 詳細は「[3. ゼロランタイム依存原則の適用範囲](#3-ゼロランタイム依存原則の適用範囲-zero-runtime-dependency-scope)」で定義します。
2. **Spec-Driven Development**
   - `spec/cases/*.json` は言語中立な公開契約であり、全バインディングで同一ケースが 100% パスすること。
3. **Safe Kanji Guard & Safe Failure**
   - バインディング層の追加により、コメント消失・URL 破損・クラッシュ（プロセス異常終了）が新たに発生してはならない。ネイティブ層で異常が起きた場合も、原文を失わない経路（フォールバックまたは例外）で処理すること。
4. **TypeScript API の安定性**
   - `toKatakana` および `KatakanaConverter` のシグネチャと挙動を維持し、Rust コアへの移行で既存利用者のコードを 1 行も壊さないこと。
5. **Rust Core が Single Source of Truth**
   - 変換ロジックは `crates/multilingual-katakana-core` にのみ実装し、バインディング層（グルーコード）は **型変換・オプション変換・エラー変換のみ** を担う。バインディング側での辞書や変換ルールの再実装は禁止。

### 2.1 Phase 0: 共通基盤の整備（v0.4.0 開発期間内・単独リリースなし）

v0.4.0 の実装 PR に先立ち、以下を完了させます。

| # | タスク | 目的 |
|---|---|---|
| P0-1 | **NAPI-RS PoC**（`convert` 1 関数のみのネイティブアドオン）を作成し、ベンチマークとバイナリサイズを計測 | Go/No-Go 判定（下記基準） |
| P0-2 | 仕様スキーマへ **任意フィールド `options`** を追加（言語フラグ・`normalizeProsody`・文字列リテラルの `exclude` のみ）し、TS/Rust 両ランナーで解釈 | デフォルト以外のオプションもバインディング横断で契約化する |

**P0-1 の Go/No-Go 基準**:

### 2.3 Phase 2: v0.5.0 — Python バインディング（PyO3 + maturin）

- **順位の根拠**: VOICEVOX ENGINE・AivisSpeech Engine・COEIROINK などの主要 TTS エンジン本体や、読み上げ Bot の多くが Python で実装されており、Node.js 以外で最も利用価値が高いターゲットです。PyO3 + maturin は wheel ビルド・クロスコンパイル・PyPI 公開の手順が最も成熟しており、Phase 1 で確立したマトリクスと適合性テストの型をそのまま流用できます。
- **API 方針**: Python の慣習に合わせた snake_case のキーワード専用引数で、TS と同一の意味論を提供します（例: `to_katakana(text, *, exclude=(), enable_english=True, ...)`、`KatakanaConverter(**defaults).convert(text, **overrides)`）。型スタブ（`.pyi`）と `py.typed` を同梱します。

### 2.4 Phase 3: v0.6.0 — C# / .NET バインディング（C ABI + P/Invoke）

- **順位の根拠**: 棒読みちゃんプラグイン、ゆかりねっとコネクター系ツール、Unity 製配信ツールなど .NET 資産の需要はあるものの、C ABI の設計（メモリ所有権・エラー伝搬）という新しい設計面を伴うため、Node/Python で配布パイプラインが安定した後に着手します。
- ここで作る **汎用 C ABI クレート（`crates/multilingual-katakana-ffi`）** は、将来の Go / Swift / Kotlin 等にも再利用可能な資産とします。

### 2.5 需要次第: スタンドアロン WebAssembly パッケージ

- ブラウザ・Deno・Cloudflare Workers 等は Pure TypeScript 実装で既にサポート済みのため、WASM 版の追加価値は「Rust コアとのビット単位の同一性」と「将来 TS 実装を縮退させる際の受け皿」に限られます。
- 利用者からの具体的な要望、または「Pure TypeScript 実装の縮退（v1.0 以降の検討事項）」が決まった時点で着手します。

## 3. ゼロランタイム依存原則の適用範囲 (Zero Runtime Dependency Scope)

`AGENTS.md` の「`package.json` の `dependencies` は常に空（`{}`）」という原則を、バインディング追加後も **暗黙に破らない** ため、適用範囲を以下のとおり明文化します。

1. **npm（`@allpaqa/multilingual-katakana`）**
   - `dependencies` は **引き続き `{}`** とします。
   - `optionalDependencies` には **本プロジェクトが同一リポジトリ・同一バージョンで公開するプラットフォーム別バイナリパッケージ（`@allpaqa/multilingual-katakana-<platform>`）のみ** を、**完全一致バージョン（`0.4.0` のように範囲指定なし）** で列挙することを許可します。
   - これらのプラットフォームパッケージは **`.node` バイナリと `package.json` のみ** を含み、JS ロジックも推移的依存も持ちません。したがって「ゼロランタイム依存」原則に違反しないものと定義します。
   - 上記以外の第三者パッケージ（`@napi-rs/wasm-runtime`、`@emnapi/*`、`detect-libc` 等を含む）を `dependencies` / `optionalDependencies` / `peerDependencies` に追加することは **禁止** します。ローダーは生成コードを使う場合でも、libc 判定等を含めて依存なしで動作する形にします。
   - `@napi-rs/cli` 等のビルドツールは `devDependencies` に限り許可します（利用者にはインストールされません）。
   - Pure TypeScript バンドル（約 86 KB）は従来どおり単独で完結し、README の「~86KB bundle」表記は JS バンドルについて引き続き正確であること。ネイティブバイナリのサイズは別途明記します。
2. **PyPI（`multilingual-katakana`）**: `pyproject.toml` の `dependencies` は空。Python 側は薄い型付きラッパーのみとします。
3. **NuGet（`Allpaqa.MultilingualKatakana`）**: パッケージ依存ゼロ。`netstandard2.0` ターゲットでも `System.Memory` 等の追加パッケージに依存しない実装（`byte[]` ベースのマーシャリング）とします。
4. **Rust クレート**: `multilingual-katakana-core` は現状どおり `regex` のみに依存します。バインディング用グルークレートの依存（`napi` / `pyo3` 等）はコアに持ち込みません。

## 4. TypeScript 公開 API の維持方針 (API Stability)

### 4.1 ドロップイン置換の構造

```text
toKatakana(text, options) / KatakanaConverter#convert / #transform   ← 公開 API（無変更）
        │
        ├─ resolveOptions()                         ← 既存 TS（無変更）
        ├─ escapeExcluded(text, opts.exclude)       ← 既存 TS（JS の RegExp 意味論を維持）
        │
        ├─ [backend = native] native.convert(escaped, flags)   ← Rust コア（exclude は空で呼び出し）
        │   └─ 失敗時 → Pure TypeScript パイプラインで再実行
        ├─ [backend = js]     既存 Pure TypeScript パイプライン
        │
        └─ restoreExcluded(result, tokenMap)        ← 既存 TS（無変更）
```

- **`exclude` の処理は JS 側に残します。** 利用者が渡す `RegExp` は JavaScript の正規表現方言（後読み・後方参照・`u`/`v` フラグ等）で書かれており、Rust の `regex` クレートでは同一の意味論を再現できないためです。JS 側で既存の `escapeExcluded` により PUA トークン化した文字列を、`exclude` 空のオプションでネイティブへ渡し、戻り値を既存の `restoreExcluded` で復元します。Rust コアのパイプラインは PUA 文字を通常文字として扱うため、この分割で出力は変わりません（差分テストで保証します）。
- ネイティブ関数に渡すのは **解決済みの真偽値フラグ 10 個と文字列のみ** とし、境界を最小化します。

### 4.2 ネイティブ経路を使わない条件（常に Pure TypeScript で処理）

以下の場合は、挙動の完全一致を優先して Pure TypeScript パイプラインを使用します。

| 条件 | 理由 |
|---|---|
| ネイティブパッケージが未インストール・読み込み失敗・自己診断失敗 | Safe Failure |
| ブラウザ / Deno / Edge / Worker 環境（`browser` 等のエクスポート条件） | Node-API 非対応 |
| 入力が `string` 型でない | 既存の例外挙動（型エラー）を維持 |
| 入力に **孤立サロゲート**（不正な UTF-16）を含む | Rust の `String` へ変換する際に U+FFFD へ置換され、原文が破損するため |
| `KatakanaConverter` のサブクラスが `resolveWord` をオーバーライドしている | 公開メソッドのオーバーライドによるカスタマイズを無視しないため |
| 環境変数 `MULTILINGUAL_KATAKANA_BACKEND=js` | 利用者による明示的な無効化（障害時の回避策） |

### 4.3 ローダーの要件

- ESM / CJS の両ビルドから動作すること（ESM では `createRequire(import.meta.url)` を使用）。
- 読み込みは **遅延かつ 1 回のみ**。読み込み後に固定入力での **自己診断**（例: `"hello"` → `"ハロー"`）を行い、不一致なら以後 Pure TypeScript を使用します。
- ネイティブ呼び出しで例外が発生した場合（Rust 側 panic は NAPI-RS の `catch_unwind` で JS 例外に変換）、その呼び出しは Pure TypeScript で再実行して結果を返します。プロセスを異常終了させてはなりません。
- 環境変数 `MULTILINGUAL_KATAKANA_BACKEND` の値: `auto`（既定: ネイティブ優先・失敗時 JS）/ `js`（常に JS）/ `native`（ネイティブ必須。読み込めない場合は例外。**CI 専用** の用途で、フォールバックによる「黙ったままのパス」を防ぐ）。
- バンドラ（esbuild / webpack / Vite）で Node 向けにバンドルされた場合も、ネイティブパッケージの解決失敗は Pure TypeScript へのフォールバックとなり、ビルドエラーにならないこと。Electron（asar）での利用方法は README に記載します。

### 4.4 追加 API の扱い

- v0.4.0 では **公開 API を追加しない** ことを既定とします。
- 実行中のバックエンドを確認する手段（例: `getBackend(): "native" | "js"`）の追加は、利用者のデバッグ需要が確認された場合にのみ、**追加のみ（非破壊）** で行います（未決事項 [8.1](#81-phase-1-着手前-v040)）。

### 4.5 Pure TypeScript 実装の位置付け

- v0.4.x の間、Pure TypeScript 実装は **第一級の実装として維持** します（フォールバック兼ブラウザ実装）。辞書・仕様の変更は従来どおり TS と Rust の両方で 100% パスが必須です。
- Pure TypeScript 実装の縮退・廃止（例: 非 Node 環境を WASM に一本化）は v1.0 以降の検討事項とし、本フェーズでは扱いません。

## 5. ターゲット別パッケージング・配布方針 (Packaging & Distribution)

### 5.1 リポジトリ構成（案）

```text
crates/
  multilingual-katakana-core/      # SSOT（公開 API は追加のみ。バインディング都合の破壊的変更禁止）
  multilingual-katakana-ffi/       # v0.6.0: 汎用 C ABI（cdylib / staticlib + C ヘッダ）
bindings/
  node/                            # 既存 TS パッケージ（公開 API・Pure TS 実装・ローダー）
    native/                        # v0.4.0: NAPI-RS グルークレート（publish = false）
    npm/<platform>/package.json    # v0.4.0: プラットフォーム別バイナリパッケージ
  python/                          # v0.5.0: maturin プロジェクト（PyO3 グルー + 型スタブ + pytest）
  dotnet/                          # v0.6.0: C# ライブラリ + xUnit テスト + NuGet パッケージ定義
```

- グルークレートはすべて Cargo ワークスペースのメンバーとし、`cargo test --all-targets` / `cargo clippy` / `cargo fmt --check` の品質ゲート対象に含めます。
- `multilingual-katakana-core` はパス依存で参照します（crates.io への公開はバインディング配布の前提としません）。

### 5.2 Node.js ネイティブ（v0.4.0）

| 項目 | 方針 |
|---|---|
| フレームワーク | NAPI-RS v3（`napi` / `napi-derive` 3.x、ビルドは `@napi-rs/cli`） |
| Node-API レベル | 使用 API で必要な最小レベル（想定: `napi4`）。高レベル API は使用しない |
| 配布方式 | メインパッケージの `optionalDependencies` に、`os` / `cpu` / `libc` フィールド付きのプラットフォームパッケージを完全一致バージョンで列挙 |

## 6. 適合性テスト戦略 (Conformance Testing)

### 6.1 共通原則

1. **単一の契約**: `spec/cases/*.json` を唯一の正とし、各バインディングは **その言語標準のテストランナー** から同ディレクトリを直接読み込みます（ケースの複製・変換生成は禁止）。
2. **判定規則の統一**: 全ランナーで `actual === expected.canonical || expected.accepted.includes(actual)`（`expected` が文字列の場合は完全一致）。既存の TS / Rust ランナーと同一です。
3. **件数の検証**: 各ランナーは `spec/cases` 内の全 JSON ファイルを列挙し、読み込んだ総ケース数と合格数を `N/N` 形式で出力します。ファイルの読み込み・パース失敗やケース数 0 は失敗扱いとします（ファイル追加時の「黙ったままの未実行」を防止）。
4. **成果物に対するテスト**: 「100% パス」は **ソースツリーではなく、配布する成果物**（npm tarball、wheel、nupkg）をクリーン環境へインストールした状態で、Tier 1 の全プラットフォームにおいて全ケースが合格することを指します。
5. **フォールバックの封じ込め**: CI では `MULTILINGUAL_KATAKANA_BACKEND=native` のように **バックエンドを強制** し、ネイティブが読み込めない場合は失敗させます（フォールバックによって偽の合格にならないようにする）。

### 6.2 バインディング別ランナー

| 対象 | ランナー | 実行対象 |
|---|---|---|
| Rust コア | `crates/multilingual-katakana-core/tests/spec_test.rs`（既存） | ソース |
| Node（Pure TS） | `bindings/node/tests/spec.test.ts`（既存、`bun test`） | ソース + パッキング済み tarball |
| Node（ネイティブ） | 同ランナーをバックエンド `native` で実行（Node.js 組み込みの `node --test` でも実行し、Bun 依存のみにしない） | Tier 1 全 8 プラットフォームのパッキング済み tarball |
| Python | `bindings/python/tests/test_spec.py`（pytest でパラメータ化） | Tier 1 全プラットフォームの wheel |
| C# | `bindings/dotnet/tests`（xUnit の Theory） | 全 RID の nupkg |

### 6.3 仕様外の追加検証

- **差分テスト（Node ネイティブ vs Pure TS）**: 仕様ケースの入力、`exclude` テストの入力、および生成コーパス（混在スクリプト、絵文字、PUA 文字、孤立サロゲート、制御文字、長文、空文字列）について、両バックエンドの出力が **完全一致** することを検証します。不一致が見つかった場合は、コアまたは TS を修正し、そのケースを `spec/cases` へ追加します。
- **オプション契約**: P0-2 で追加する `options` 付きケースにより、言語フラグ・`normalizeProsody`・リテラル `exclude` をバインディング横断で検証します。`RegExp` 系 `exclude` は各バインディングの個別テスト（既存 `exclude.test.ts` を両バックエンドで実行）で担保します。
- **Safe Failure の不変条件**: `failure_modes.json` / `kanji_guard.json` の全ケースは全バインディングで必須（例外扱い・スキップ禁止）とします。

### 7.4 バージョニング戦略

- **ロックステップ方式**: コアクレート、全グルークレート、全配布パッケージ（npm メイン + プラットフォーム、PyPI、NuGet）は **常に同一バージョン** とします。バインディングのみの修正であっても全体のパッチバージョンを上げます（利用者が「どのバージョンのコアか」を迷わないことを優先）。
- `docs/RELEASE_PROCESS.md` 第 3 項の「同期更新が必要な箇所」に、各フェーズで追加されるマニフェスト（プラットフォームパッケージの `package.json`、メインの `optionalDependencies`、グルークレートの `Cargo.toml`、`pyproject.toml`、`.csproj`）を追記します。手作業の漏れを防ぐため、全マニフェストのバージョン一致を検証するスクリプトを CI に追加します。
- プレリリース表記の対応: npm / Cargo / NuGet は `0.4.0-rc.1`、PyPI は PEP 440 に従い `0.4.0rc1`。
- 0.x 系の間、Rust コアの公開 API の破壊的変更はマイナーバージョンで行い、CHANGELOG と README の **Breaking change** 表記で明示します（v0.3.0 と同じ運用）。各バインディングの公開 API は、それぞれのエコシステムの SemVer 慣習に従い破壊的変更を避けます。

### 7.5 公開順序

プラットフォーム別パッケージが未公開のままメインパッケージが公開されると、`optionalDependencies` の解決に失敗します。以下の順序を `publish.yml` で強制します。

1. プラットフォーム別パッケージ（全 Tier 1）を公開
2. すべて成功した場合のみ、メインパッケージ `@allpaqa/multilingual-katakana` を公開
3. （v0.5.0 以降）PyPI・NuGet は npm と独立したジョブで公開し、いずれかの失敗時はリリースノートに明記して再実行する
